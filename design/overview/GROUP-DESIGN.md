# 分组（Group）功能设计调研

> 状态：**调研，未实现**
> 触发：`(层, 类, 实例, 版本)` 四元组天然是四个可分组维度；
> 且需要「动态把常用的跨层实例聚成一组，用面层面板展示以便应用」
> 所有数字均为实测，非估算

---

## 0. 结论先行

| 判断 | 结论 |
|---|---|
| 分组是不是新功能 | **不是** —— Dock 的 5 个 tab（常用/开发/系统/工具/外网）已经是分组，只是静态、手写、33/48 成员失效 |
| 该建什么 | 一个**分组定义层**（GroupDef），Dock tab 和面层面板都是它的**视图** |
| 分组对象 | 不只是「实例」，而是四元组的任意切片：按层 / 按类 / 按实例 / 按版本，以及跨层混合 |
| 关键风险 | 跨层聚合的权限/副作用必须**如实上报最大值**，不能因为「分组了」就降低 |
| 最大收益 | 把「33 个失效的 dock 成员」这类静默断链变成**界面上可见的缺口** |

一句话：**分组不是 UI 上的标签，是对 `(层,类,实例,版本)` 的查询 + 对成员的诚实盘点。**

## 1. 现状调研：已经在用的是什么

### 1.1 六种「类分组」机制，各管一摊

| 机制 | 位置 | 取值 | 用途 | 局限 |
|---|---|---|---|---|
| `family` | 类上 | 28 种（point 11 / line 2 / surface 4 / body 7 / field 5） | UI 家族筛选 | **只有一个维度**，且每层独立 |
| `priority` | 类上 | `P0` / `P1` | 显示排序 | 只有 point 和 field 有 |
| `status` | 类 / 实例 | `active` / `draft` | 状态 | 不分层，也不分组 |
| `effect` | 类上 | 见 §1.2 | 风险 | **字段语义混用** |
| panel `group` | 面板 | `inspect`/`edit`/`ai`/`data`/`system` | 面板分组 | 只服务面板，14 个面板 |
| `aliases.json` | 独立文件 | 3 类别名 + 10 实例别名 + 4 待审 | 名称解析 | 不是分组，是「多名字→一个东西」 |

**没有一个是通用分组。** 每个都是为某个具体 UI 临时加的单一维度。

### 1.2 实测发现一：`effect` 一个字段装了两个轴

| 层 | `effect` 取值 | 实际含义 |
|---|---|---|
| point | `L0` 8 · `L1` 12 · `L2` 1 | 副作用等级 |
| line | `L1` 13 | 副作用等级 |
| surface | `L0` 16 | 副作用等级 |
| body | `L1` 9 · `L2` 20 | 副作用等级 |
| **field** | **`A0` 7 · `A1` 10 · `A2` 6** | **自主度，不是副作用** |

`L` 和 `A` 是**两个独立的轴**：L 说「会造成多大改动」，A 说「允许自主到什么程度」。

一旦做跨层分组（field + point 混在一起），拿 `effect` 排序或取最大值就是**拿苹果比橘子**。
分组必须把两个轴分开聚合，否则会出现「这个组最坏是 L0」这种漏报。

### 1.3 实测发现二：Dock 的「常用」分组已经存在，但 33/48 成员是死的

现有 5 个 dock tab、48 个 tile：

```
常用 12 · 开发 8 · 系统 10 · 工具 8 · 外网 10
```

tile 结构：`{ id, tab, name, sub, kind, icon, hotkey, target, effect }`
其中 `target` 指向实例 id，`kind` 是 `flow`(23) / `point`(25)。

**逐个核对 target 是否真实存在：**

| 结果 | 数量 |
|---|---:|
| 精确命中真实实例 | **15** |
| 指向不存在的 id | **33** |

33 个失效的例子：

```
open.terminal@r1         json.format@r1        text.regex@r1
sys.metrics.snapshot@r1  sys.cpu.stats@r1      sys.gpu.stats@r1
settings.open@r1         flow.run.logs@r1
inst.site-openai@r1      inst.invoice-company@r6
```

这些不是笔误 —— 它们是**产品想要但还没造的能力**（终端、JSON 格式化、正则、系统指标、站点实例）。
和体层 composition 的 109 条悬空引用是同一类东西：**需求，没人追踪**。

Dock 是软件最显眼的入口，**31% 的按钮点了会找不到东西**，而界面上没有任何提示。

### 1.4 实测发现三：版本维度是真实存在的

287 个实例的 `rev` 分布：

| rev | 1 | 2 | 3 | 4 | 5 | 6 |
|---|---:|---:|---:|---:|---:|---:|
| 实例数 | 240 | 29 | 10 | 4 | 1 | 3 |

**47 个实例有多次修订。** 所以「按版本分组」不是空想：
它在回答「这个组里的东西，哪些已经改过了 / 我想固定在 r2 那一版」这类真实问题。

### 1.5 实测发现四：`family` 跨层会撞

28 个 family 里，`window` 同时出现在 **point**（`win.window.control` 等）和
**body**（`body.window-layout` 等）。

所以跨层查询如果只写 `family = window`，会把「窗口控制」和「窗口布局」混在一起。
**查询必须能带层约束，或者至少能看出命中了哪几层。**

## 2. 四元组 = 四个分组维度

`层.类.实例@rN` 的每一段都是一个合法的分组键：

| 维度 | 键 | 规模 | 典型问法 |
|---|---|---:|---|
| 层 | `layer` | 5 | 「所有点层能力」 |
| 类 | `layer.class` | 102 | 「所有用键盘的类」 |
| 实例 | `layer.class.instance@rev` | 287 | 「我常用的那 8 个」 |
| 版本 | `@rev` | 1–6 | 「哪些改过 / 固定在 r2」 |
| **跨层** | 任意组合 | — | 「早上一套：截图→OCR→翻译→贴回」 |

前四个是**同质分组**（成员同一类型），第五个是**异质分组**（成员跨层）——
后者才是维护者要的「常用跨层实例形成一个组」。

两种分组的行为不一样：

| | 同质分组 | 异质分组 |
|---|---|---|
| 排序 | 按类内顺序、priority | 需要统一的行模型 |
| 聚合 | 单轴（只看 L 或只看 A） | **双轴都要报**（L 和 A 分开） |
| 应用到 | 直接跑 | 每个成员发出**不同类型的意图** |

## 3. 分组对象模型

### 3.1 三种定义方式

```ts
type GroupDef =
  | { kind: 'static';  members: string[] }              // 手挑，全部钉版本
  | { kind: 'dynamic'; query: GroupQuery }              // 规则，渲染时求值
  | { kind: 'hybrid';  query: GroupQuery;              // 规则 + 手工增删
      pinned: string[]; excluded: string[] }
```

- **static**：成员是完整 atom id（含 `@rN`），天然钉住版本 → 可复现
- **dynamic**：只存查询，每次打开重算 → 自动跟随变化
- **hybrid**：查询做底座，`pinned` 强制加入、`excluded` 强制剔除 → 最实用

### 3.2 查询维度（全部映射到四元组或其上的字段）

```ts
interface GroupQuery {
  // ── 四元组本体 ──
  layer?: AtomLayer[]
  className?: string[]                       // 不带层前缀的类名段
  instance?: string[]                        // 精确实例名段
  rev?: { min?: number; max?: number; onlyLatest?: boolean }

  // ── 类/实例上的字段 ──
  family?: string[]
  priority?: string[]
  effect?: string[]                          // 副作用 L0–L3
  autonomy?: string[]                        // 自主度 A0–A2（从 field 的 effect 拆出来）
  status?: string[]

  // ── 运行派生的（「常用」靠这个）──
  recentlyRunDays?: number
  usageCountGte?: number
  lastRunStatus?: ('ok' | 'warn')[]

  // ── 文本 ──
  text?: string                              // 匹配 name / description
}
```

**「常用」不需要新数据源** —— `LayerStore.runs()` 已经记录了
`{ id, classId, instanceId, status, elapsedMs, createdAt }`。
按 `instanceId` 计数就是使用频次。

⚠️ 但现在**一条运行记录都没有**（新数据目录）。所以「常用」组第一次打开时
应该显示「还没有运行记录，先去跑几次」，而不是一个空列表 —— 空列表会被误解成 bug。

### 3.3 分组自己的命名

分组**不是 Atom**，不该挤进 `层.类.实例@rev` 的命名空间：

```ts
type GroupId = `group.${string}`      // group.morning-routine
```

理由：

- 分组**没有层**（它跨层），塞进 5 个层里任何一个都是说谎
- 分组**不执行**，它没有 `run`，只有「展开成成员列表」
- `parseAtomId('group.x')` 必须返回 `null` —— 这个隔离要守住

分组自己的版本用 `rev` 字段（不进 id），因为它不参与跨实体引用。

## 4. 八个分析维度

### 4.1 维度一：分组对象

| 可分组 | 同质 | 异质 |
|---|---|---|
| 类（跨层） | ✓ | ✓ |
| 实例 | ✓ | ✓ |
| 版本 | ✓ | ✓ |
| **运行结果** | ✓ | ✓ |

### 4.2 维度二：定义方式
静态 / 动态 / 混合（见 §3.1）。

### 4.3 维度三：用途

| 用途 | 需要什么 | 现状 |
|---|---|---|
| **查找** | 查询 + 计数 | 无 |
| **展示** | 行模型 + 排序 | 无 |
| **应用**（点一下就执行） | 每个成员发**类型化意图** | 无 |
| **批量**（全跑一遍） | 逐个执行 + 汇总 | 无 |
| **权限范围** | 组级 effect/autonomy 上限 | 无，但 `field.guard` 已能做判定 |
| **盘点缺口** | 成员失效检测 | 无，这正是 33/48 的痛点 |

### 4.4 维度四：持久化范围

| 范围 | 例子 | 能不能改 |
|---|---|---|
| 内置 | 「全部 P0」「未实现」「高副作用」 | 只读 |
| 工作区 | 「早上一套」「发布前检查」 | 可编辑 |
| 会话临时 | 搜索结果的临时聚合 | 不落盘 |

### 4.5 维度五：生命周期

| 类型 | 成员何时确定 | 风险 |
|---|---|---|
| 静态 | 创建时 | 成员被删/改名 → 失效（Dock 现状） |
| 动态 | 每次渲染 | 结果不可复现，但永远新鲜 |
| 混合 | 每次渲染 + 钉住项 | 两者兼得 |

**必须有 `broken: string[]` 字段**：静态组里指向不存在 id 的成员要能被点名，
而不是静默消失。这是 Dock 现在最大的问题。

### 4.6 维度六：权限与副作用聚合（最重要）

跨层组必须**在两轴上分别取最大值**，并且**永不低估**：

```ts
interface GroupRisk {
  maxEffect: 'L0' | 'L1' | 'L2' | 'L3' | null   // 副作用轴
  maxAutonomy: 'A0' | 'A1' | 'A2' | null        // 自主度轴
  worstMember: { id: string; why: string } | null
  /** 聚合不到位时如实说明，不允许静默返回 null */
  incomplete?: string
}
```

规则：

1. 两轴**分开算**，不合并成一个数字
2. 只要有一个成员是 L3 未批准 → 整组不能一键执行
3. **组级权限不是授权**：执行时每个成员仍要单独过 `field.guard`。
   组只是「预检」，不是「豁免」
4. 聚合必须能回答「为什么这个组是 L2」→ 指出最坏成员

### 4.7 维度七：失效与漂移

| 情况 | 怎么处理 |
|---|---|
| 成员 id 不存在 | 进 `broken`，界面显示为禁用 + 原因 |
| 成员版本过期 | 显示 `r1 → r3`，提供「升级固定版本」动作 |
| 成员所属类已删 | 同「不存在」，但原因写「类已删除」 |
| 查询命中 0 条 | 明确说「查询无结果」，不是空列表 |

### 4.8 维度八：与 id 方案的关系

- 组 id 用 `group.` 前缀，**必须被 `parseAtomId` 拒绝**
- 组成员用完整 atom id（含 `@rN`）→ 天然钉版本
- 动态组的查询用**类名段 / 实例名段**（不含层前缀），层由 `layer` 字段单独给
- 迁移到 3 段 id 之后，组数据要跟着重写一次（和 `panel.content` 同批）

## 5. 关键洞察：Dock tab 就是分组，应该统一

现在有两套「一组快捷入口」：

| | Dock tab | 设想的 Group |
|---|---|---|
| 分组名 | `common` / `dev` / `system` / `tools` / `web` | 任意 |
| 成员 | 48 个 tile，`target` + `kind` + `hotkey` | AtomRef 列表 |
| 动态 | ❌ 全手写 | ✓ 查询 |
| 失效检测 | ❌ 33/48 死了没人知道 | ✓ `broken` |
| 跨层 | ✓（flow 23 + point 25） | ✓ |
| 展示 | Dock 网格 | 面层面板（table / card-grid） |

**它们是同一个东西的两个视图。**

建议：

```ts
type GroupView = 'dock' | 'table' | 'card-grid' | 'palette'

interface GroupDef {
  id: GroupId
  name: string
  view: GroupView          // ← 决定用哪个面层 pattern 渲染
  ...
}
```

这样：

- Dock 的 5 个 tab 变成 5 个 `view: 'dock'` 的组
- 「常用」从静态手写变成 `{ kind: 'dynamic', query: { usageCountGte: 1 } }`
- 同一个组换个 `view` 就能用面板展示 —— 这正是维护者要的「用面层面板展示方便应用」
- **33 个失效成员立刻在 Dock 上显示为禁用** —— 静默断链变成可见缺口

## 6. 与面层的连接：「应用」= 面板挂载

结合 `SURFACE-BODY-SEMANTICS.md` 的结论：

```text
GroupDef（查询）
   └→ Panel（容器：mode / width）
        └→ SurfacePattern（table / card-grid）
             └→ 每行一个成员，发出类型化意图
```

每个成员的「应用」动作按层不同：

| 成员层 | 点击后发出的意图 |
|---|---|
| point | `runPoint` |
| line | `runFlow` |
| surface | `openPanel` |
| body | `assemble` |
| field | `runField` |

所以分组面板的行模型必须带 `intent`，不能只有「名字 + 图标」。

```ts
interface GroupRow {
  id: string                  // 完整 atom id
  layer: AtomLayer
  className: string
  instance: string
  rev: number
  name: string
  effect: string | null       // 该成员自己的
  intent: SurfaceIntent       // 点它要干什么
  disabled?: string           // 失效原因，有值就禁用
}
```

## 7. 风险清单

| 风险 | 后果 | 对策 |
|---|---|---|
| **跨层聚合漏报** | 组显示 L0，实际含 L2 → 用户以为安全 | 双轴分别取最大，`incomplete` 显式标记 |
| **组级权限当授权** | 组通过了就不再逐项检查 | 明文规定：组只做预检，执行时逐项过闸 |
| **静态成员静默失效** | Dock 现状：31% 按钮是死的 | 强制 `broken` 字段 + 界面禁用态 |
| **`effect` 字段两轴混用** | 跨层排序/取最大值算错 | 拆成 `effect` + `autonomy` 两个字段 |
| 动态组结果不可复现 | 同一天两次打开内容不同 | 混合模式 + 「钉住为静态组」动作 |
| 查询命中 0 条被当成空 bug | 用户以为功能坏了 | 区分「无结果」与「无数据源」两种文案 |
| 组嵌套成环 | 无限展开 | 嵌套深度上限 + 环检测（`field.simulate` 已有先例） |
| 「常用」没有数据 | 新装软件打开是空的 | 明确提示「还没有运行记录」 |

## 8. 分阶段落地

| 阶段 | 内容 | 依赖 | 能验证什么 |
|---|---|---|---|
| **1** | 拆 `effect` 为 `effect` + `autonomy` 两字段 | 无 | 跨层聚合不再混轴 |
| **2** | `GroupDef` 类型 + 内置组（全部 P0 / 未实现 / 高副作用 / 最近改动） | 阶段 1 | 查询与聚合正确 |
| **3** | 成员解析 + `broken` 检测 | 阶段 2 | **33 个失效 dock 成员被点名** |
| **4** | 把 Dock 的 5 个 tab 改成 `view: 'dock'` 的组 | 阶段 3 | 现有功能不退化 + 缺口可见 |
| **5** | 面层面板视图（table / card-grid） | 依赖面层 render | 「用面板展示」落地 |
| **6** | 动态「常用」组（基于 runs） | 需要真实运行数据 | 使用频次驱动 |

**阶段 1–3 不依赖面层/体层的任何未完成工作**，可以立刻做。
阶段 3 一做完，Dock 上 33 个死按钮就会变成 33 个灰色带原因的条目 —— 这是最直观的收益。

---

## 9. 明确不做的事

| 不做 | 理由 |
|---|---|
| 把组塞进 `层.类.实例@rev` 命名空间 | 组没有层、不执行，塞进去是语义污染 |
| 组级权限代替逐项闸门 | 一次授权放行整组 = 漏报副作用的经典路径 |
| 把 `L` 和 `A` 合并成单一「风险分」 | 两个正交的轴，合并后无法解释「为什么被拒」 |
| 动态组默认钉版本 | 那就退化成静态组了；要钉是用户的显式动作 |
| 让组成为第六个「层」 | 层是执行语义的分层，组是查询，不是同一类东西 |
| 静默丢弃失效成员 | Dock 现在的 33/48 就是这么烂掉的 |

---

## 10. 一页总结

- **分组不是新功能**：Dock 的 5 个 tab 已经是了，只是静态、手写、31% 死链
- **四元组给四个维度**：层 / 类 / 实例 / 版本，加一个跨层混合
- **三种定义**：静态（可复现）/ 动态（永远新鲜）/ 混合（最实用）
- **两个轴**：`effect`（副作用）和 `autonomy`（自主度）必须分开聚合，永不低估
- **一个统一**：Dock tab 和面层面板是同一个 `GroupDef` 的两种 `view`
- **一条铁律**：失效成员必须被点名，不能静默消失
